# @local/dsh-voice-player · v0.6.0

> 语音消息 + 语音通话：让 agent 开口说话（`voice_say`），让用户录一段发出去，并提供一套本机语音服务（ASR + TTS）的生命周期管理。

## 零、一次通话怎么跑（照这个做，别临场发挥）

> 这一节是**操作手册**：按顺序做就不会出错。原理、坑、历史都在后面各章。
> **只想快速上手 / 交给别人用 → 直接看 [使用说明.md](使用说明.md)**（一页版：开工前五件事 + 两种模式怎么走 + 不能做什么 + 排错）。本节保留更细的判据。

### 0.1 开始之前必须知道的五件事

| # | 事实 | 意味着什么 |
| --- | --- | --- |
| 1 | **开始信号**是对话里出现「（语音通话已开始）」 | 看到它才进入通话模式；没看到就按普通打字回合处理，不要自己开口 |
| 2 | **结束信号**是 `{"type":"end"}`，而且**只认本次通话的 end** | inbox 里躺着前几通电话的 end；只有「最后一条 `start` 之后」的 end 才算数。静音、很久没新句都**不是**结束信号 |
| 3 | **两条通道**：用户说的话进本会话的 `voice-inbox.jsonl`（文件），我说话走 `voice_say`（工具） | 我不"听"音频，我读文件；路径由工具回给我（`inbox` 字段），不用自己拼 |
| 4 | **状态要问工具**：`voice_call_status` | `inCall=true` 才是通话中；它同时把心跳刷一下，状态灯才显示「聆听」 |
| 5 | **半双工 + 回合制**：我播语音时用户说话会被丢掉；通话期间不许主动结束回合 | 要么我说、要么他说，不能同时；只有本次通话的 `end` 才能收尾 |

**还有一个前提**：TTS 服务（18082）活着。`voice_say` 会自己 `ensure('tts')` 拉起来，失败会直接返回错误，不会静默。

**反过来也成立**：没有「（语音通话已开始）」就不是通话，用户只是打字——**回文字，不要发语音**。用户要听语音会明说（「说句话」「读给我听」）。

### 0.2 一步一步

| 步 | 做什么 | 用什么 | 怎么算做完 |
| --- | --- | --- | --- |
| ① | **确认还在通话** | `voice_call_status` | 拿到 `inCall=true`（同时刷新心跳、已读行号自动同步） |
| ② | **说开场白**（接通后客户端只等 **3 秒**再开麦，要马上说） | `voice_say`：「你好，我是小肥鱼，我听着呢。」 | 返回 `【语音 N.Ns】http://…` |
| ③ | **等新句**（不要 sleep + 读文件） | `voice_wait`（`timeoutSec` 默认 20，最长 25） | 返回 `lines`（新句）/ `ended` / `timedOut`；已读行号已自动写回 |
| ④ | 若是 `speech`：先定答什么 | 思考，不用工具 | 一句话能说清要点 |
| ⑤ | 若要动手干活（查资料 / 改文件 / 派子代理） | 先 `voice_say`：「我这就去办」 | 用户不会只听到沉默 |
| ⑥ | **回语音** | `voice_say`（**一次 ≤120 字，约 30 秒**） | 返回 `【语音 N.Ns】`；超过 30 秒会带回 `warn` |
| ⑦ | 内容太长（>30 秒） | 拆成 2–3 次 `voice_say`，**连着发完，中间不夹 `voice_wait`** | 后续组在后台合成、客户端排队连播，前后接得上（2026-11-05 用户定） |
| ⑧ | **回到第 ③ 步** | — | **不结束回合，继续等下一句** |
| ⑨ | `ended=true` 或 `inCall=false` | — | 用**文字**回一句收尾，回合结束 |

### 0.3 四个最容易翻的车（都踩过）

| 现象 | 真因 | 正解 |
| --- | --- | --- |
| 正在通话，却被判成「已挂断」 | 读到了**上一通**留下的 `end` | 只认最后一条 `start` 之后的 end；`voice_call_status` 已经这么判了，别自己数行 |
| 电话早挂了，我还在一条条念语音 | 只在"找新话"时读 inbox，没看通话状态 | **每次发语音前先调 `voice_call_status`** |
| 用户说"你怎么不说话"，同一句话说了两遍 | 长播报把那几十秒的麦克风关了，用户的话被丢或排队 | 单次 ≤120 字；长的拆开**一次连发**，别等一段播完再合成下一段 |
| `voice_say` 报 `say 18082 -> 500` | 同一个 TTS 实例被并发打崩（CUDA device assert，一次就废） | 服务端已改为**逐句合成 + 串行锁**；仍失败就重启 18082 |

### 0.4 接口速查

| 要什么 | 用什么 |
| --- | --- |
| 通话还在不在 / 刷心跳 | 工具 `voice_call_status`（无参数，返回 `inCall` / `callId` / `sessionId` / `inbox` / `lastEvent` / `nextLine` / `hint`） |
| **阻塞等下一句** | 工具 `voice_wait`（`timeoutSec` 1–25，默认 20；返回 `lines` / `fromLine` / `toLine` / `sessionId` / `inbox` / `ended` / `timedOut`） |
| 说一句话 | 工具 `voice_say`（`text` ≤120 字/≤30 秒；超过会带 `warn`） |
| 用户说了什么 | 本会话的 `…\输出\calls\<sessionId>\voice-inbox.jsonl`（每行 `{"t":…,"type":"start"|"speech"|"end","text":"…","callId":"…"}`） |
| 读到第几行 | 同目录 `voice-inbox.read`（**由上面两个工具自动维护**，不用手写） |
| 通话状态端点 | `GET/POST /voice-call/state`（客户端上报 `active` + `callId`，宿主记录） |
| 心跳端点 | `GET /voice-call/heartbeat` → `{alive, age, busy}`（`alive` = 心跳在 3s 内；`busy` = 正在合成语音） |

### 0.5 依赖与移植（打包给别人之前先看这一节）

| 依赖 | 写死的路径 | 用在哪 |
| --- | --- | --- |
| TTS 主后端 | `D:\py-tts\qwen_tts_server.py` + `.venv-qwen` | 18082，GPU 的 Qwen3-TTS |
| TTS 备份后端 | `D:\py-tts\tts_server.py` + `.venv`（CosyVoice2） | `cpu` / `mix` 档 |
| 参考音色 | `D:\py-tts\assets\voice-me.wav` | 克隆音色 |
| ASR | `D:\py-asr\asr_server.py` + `.venv` + `models\Qwen3-ASR-0.6B` | 18080，转写 |
| ffmpeg | `D:\Harness工作区\tools\bin\ffmpeg.exe`；插件另用 `D:\py-asr\.venv\...\imageio_ffmpeg` | 拼接、转码 |
| 通话文件通道 | `D:\Harness工作区\会话\流式语音输入可行性\输出\calls\<sessionId>\`（按会话隔离：`voice-inbox.jsonl`、`voice-inbox.read`、`voice-heartbeat.txt`） | 用户说话、已读位置、心跳 |

- 这些路径**全部写死在 `index.js` / `services.js` 里**：换机器要么复制同样的目录结构，要么改这几处常量；

- 包里**不含**模型和音色文件，只有插件代码（约 100 KB）；对方没装 `D:\py-tts` / `D:\py-asr` 时，插件能加载但一说话就报错。

## 二、语音通话（重点）

### 2.1 入口

独立悬浮条（默认在模型监控条上方，`right:18px / bottom:70px`），从左到右：

1. **齿轮** —— 打开「语音服务设置」面板（居中显示）；
2. **状态灯 + 文字** —— 灰「启动服务」/ 绿「语音服务」。**左键单击不动作（防误触），右键弹出菜单**，里面点「启动语音服务 / 关闭语音服务」；
3. **聆听 / 忙线 / 准备中** —— 仅通话中显示：
   - 灰「准备中」= 接通后前 **3 秒**（麦克风还没开）；
   - 绿「聆听」= 麦克风在采集 **且** agent 真的在等你说话（它正卡在 `voice_wait` 里，心跳每 400ms 刷一次）；
   - 黄「忙线」= 其余全部情况：正在想、正在合成语音、正在播报、正在转写——**这时候你说话只会被排队或丢掉**；
   - 判据落在 `/voice-call/heartbeat` 的 `alive`（心跳新鲜度）+ `busy`（是否正在合成）两个字段上，见 §2.4.5；
4. **电话按钮（四态）**：

| 状态 | 颜色 | 说明 |
| --- | --- | --- |
| 服务或模型未完全就绪 | 灰、不可点 | 提示「服务或模型未就绪」 |
| 就绪、未通话 | **绿** | 可拨打 |
| 刚点下的 3 秒缓冲 | **蓝（连接中）** | 防误触 |
| 通话中 | **红** | 点击挂断 |

5. 整根条**可拖动**（按住拖动，位置固定到屏幕坐标）；
6. **打断按钮**：通话中在条下方常驻（不透明黄底、与条同宽）。**只有我在播报时点它才有效**——立刻停掉播放、**清空排队中的后续语音**、麦克风回到「聆听」；没在播时点了无反应。

### 2.2 启动服务（自动预热）

右键状态灯 → 菜单里点「启动语音服务」时，插件会：

1. 依次 `ensure` ASR（18080）与 TTS（18082）；
2. **预热**：给 ASR 发一段 0.2 秒静音触发模型加载；给 TTS 发一句**带时间戳的唯一文本**触发合成模型加载（绕开缓存）；
3. 全部就绪后灯变绿、电话可点。

**启动即预热**：服务起来后会立刻做一次真实加载（TTS 发一句唯一文本合成、ASR 发 0.2 秒静音转写；GPU×2 时两个 TTS 实例都预热），所以「已加载」而不是干等。
首次冷启动约十几秒（模型加载），之后热态：TTS 单句约 **1.2 秒**，ASR 转写亚秒级。

> 预热文本带时间戳，**故意绕开合成缓存**——早先用固定的「你好」会命中缓存，服务直接吐 mp3、模型根本没加载（tooltip 一直显示「模型未加载」）。

### 2.3 一次通话的完整流程

| 步 | 发生什么 |
| --- | --- |
| ① 点电话 | 先写一行 `{"type":"start","callId":…}`（本通电话的锚点）、注入「（语音通话已开始）」+ 操作手册指针、POST 状态给宿主；然后开始录音 |
| ② 说话 | 静音 **2 秒**（`call.silenceMs`，可调 600–3500）判定一句结束 → 16k WAV → ASR 转写 |
| ③ 过滤 | 本地规则丢杂音（字数 <2、纯语气词、单字重复），毫秒级、不走网络 |
| ④ 写入 | 追加一行到 `voice-inbox.jsonl`（`{"t":…,"type":"speech","text":"…","callId":…}`） |
| ⑤ 读取 | agent 用 `voice_wait` 阻塞等新行（或 `voice_call_status` 看状态），读到新句就用 `voice_say` 回 |
| ⑥ 挂断 | 写入 `{"t":…,"type":"end","callId":…}` 并 POST 状态；同时调 `session.cancel()` **强制中止回合**（不依赖 agent 读到），再停麦克风 |

### 2.4 agent 侧硬性回合约定

> **这些规则写在哪**：插件注册的系统提示段（`index.js` 的 `ctx.systemPrompt.section`，`name: 'voice-player'`），每轮都可见、不占对话气泡。
> 接通时客户端**只往会话里注入一句「（语音通话已开始）」**——说明文字不进对话框（2026-11-04 用户要求，气泡里那坨字很难看）。
> 改规则 = 改 `index.js` 里那个数组，改完重启客户端。

> **通话期间不得主动结束回合。**
>
> - 收到「（语音通话已开始）」→ 第一句先说「你好，我是小肥鱼，我听着呢」；
> - 之后每回完一句语音，**立刻继续等新句**（`voice_wait`），不要以文字回复收尾；
> - 中途去干活（查资料、改文件、派子代理）后，**必须回到 `voice_wait`**；
> - 等到本通电话的 `end`（或 `voice_call_status` 报 `inCall=false`）才是挂断，这时才结束回合；
> - **每轮开头、以及每次发 `voice_say` 之前，先调 `voice_call_status`**（见 §2.4.5）；
> - **要动手做任务时，先用 `voice_say` 说一句**（例如「我这就去办」），再开始查资料/改文件/派子代理——用户不会只看到沉默，也不会误以为通话断了。

这条专门治「吩咐完活就顺手把会话结了」的老毛病。

### 2.4.5 通话状态与心跳：`voice_call_status`

**这是干嘛的**

两件不同的事以前混在一起，结果是：电话早就挂了，agent 还在一条条发语音（2026-11-04 实测，挂断 10 分钟后连发 4 条）。

| 信号 | 谁写 | 说明什么 |
| --- | --- | --- |
| **通话状态** `callState` | 客户端，接通 / 挂断各 POST 一次 `/voice-call/state` | 这通电话还在不在 |
| **心跳** `voice-heartbeat.txt` | agent 每次调 `voice_call_status` 时写一次 mtime | agent 此刻还在听（客户端据此把状态灯切回「聆听」） |

宿主把两者合起来给 agent 两个工具：

- **`voice_call_status`（无参数）**——调一次 = 刷一次心跳 + 读一次通话状态 + 同步已读行号；
- **`voice_wait`（`timeoutSec` 1–25）**——阻塞等下一句，有新行 / 挂断 / 超时立刻返回；等待期间每 400ms 刷心跳，所以状态灯一直亮「聆听」。

**返回什么**

| 工具 | 字段 | 含义 |
| --- | --- | --- |
| `voice_call_status` | `inCall` | 客户端报告的实时状态，只有通话中才是 `true` |
| | `callId` | 本通电话的 id，与 inbox 里 `start`/`end` 的 `callId` 一致 |
| | `lastEvent` | inbox 最后一条的类型与年龄，如 `speech@3s`、`end@95s`、`none` |
| | `nextLine` | 已读到的行号（同时写进 `voice-inbox.read`） |
| | `hint` | 一句话结论，照着它行动即可 |
| `voice_wait` | `lines` | 新出现的行（`{type,text,callId}`），没新句就是空数组 |
| | `fromLine` / `toLine` | 这次覆盖的行号区间，已自动写回 `.read` |
| | `ended` | 本次变化里有没有 **本通电话** 的 `end` |
| | `timedOut` | 是不是等满了 `timeoutSec` 还没动静 |

**历史 end 不会再骗人**：inbox 里前几通电话的 `end` 一直留着，所以判定改成了「**只认最后一条 `start` 之后**的 end」——每通电话开始时客户端会写 `{"type":"start","callId":…}`，`voice_call_status` 用同一个 `callId` 对齐；旧格式（没有 start 的记录）则只信客户端上报的 `active`。

**状态灯到底怎么算的（2026-11-04 修正）**

| 灯 | 条件 |
| --- | --- |
| 灰「准备中」 | 通话中，且接通还不到 **3 秒**（麦克风还没开） |
| 绿「聆听」 | 麦克风在采集 **且** agent 心跳新鲜（3 秒内）**且** 它没在合成（`busy=false`） |
| 黄「忙线」 | 其余全部：agent 在想事、在合成语音、在播报、或正在上传转写 |

两条输入：

- `alive`：agent 只要在 `voice_wait` 里等，心跳每 400ms 刷一次 → 灯一直是绿的；它一停下来想事，3 秒后自动转黄（这是**故意**的，告诉用户"现在说话会被排队"）；
- `busy`：`voice_say` 合成期间宿主把计数加一（`finally` 里减一），所以从"开始合成"到"合成结束"全程黄灯，不用等音频真的响起来。

> 以前只按心跳算，agent 在合成语音时灯仍显示「聆听」，用户以为能插话，其实那几十秒的话全被吞了。

**什么时候用（硬性）**

1. **通话回合的第一件事**：先调它，拿到 `inCall` 再决定这一轮用语音还是文字；
2. **每次要发 `voice_say` 之前**：再调一次——挂断随时可能发生，前面那次不算数；
3. **干活回来继续通话前**：调一次，顺便刷新心跳，状态灯不至于一直挂在「忙线」。

**判据（别靠记忆）**

- `inCall === true` → 通话中，正常用语音回；
- `inCall === false` → **电话已挂断**：不要发语音，改文字回复，**并且结束回合**；
- 判断"是不是这通的 end"交给工具：它只认最后一条 `start` 之后的 end。**别自己数行号、别自己比时间戳**——那正是 2026-11-04 误判的根源（历史 end 停在 349/353/355 行，新一通在 356 行之后）；
- 没有活跃状态也没有本通的 `end` → 按已挂断处理（宁可少发一条语音，不要对着挂掉的电话念）。

> 本节补的是 §2.4 的反面：§2.4 管「读到 `end` 才结束回合」，本节管「没在通话里就别开口」。两条合起来才完整。

**实现位置**

- 客户端：`callPostState(true/false)` 上报 `active` + `callId` + `sessionId`；`callPostInbox('start'/'end', '', { callId })` 在接通 / 挂断时各写一行——`start` 是"这通电话从哪一行开始"的锚点；
- 宿主：`/voice-call/state` 端点（POST 写状态、GET 读状态 + 心跳年龄 + 本会话 inbox 路径）、`voice_call_status` 与 `voice_wait` 两个工具、`callWindow()` 判定本通电话的边界；
- 通话文件：`…\输出\calls\<sessionId>\`（按会话隔离；心跳 `voice-heartbeat.txt` 是一串毫秒时间戳，取值只看 mtime）。

> 改了 `client.js` / `index.js` 要**重启客户端**才生效；只改服务端 `D:\py-tts\*.py` 则重启对应服务即可。

### 2.5 读取位置标记

每个会话自己的 `calls\<sessionId>\voice-inbox.read` 保存一个数字 = agent 已读到第几行。
**现在由工具自动维护**：`voice_call_status` 与 `voice_wait` 每调一次就把当前行数写回去（2026-11-04 之前靠 agent 手写，结果滞后了 14 行，下一次接手的人一进来就撞到旧 `end`）。
手动读它也还有用——事后核对「哪句读了、哪句漏了」。

### 2.6 长回复怎么念（流水线：边播边合成）

**流程**（2026-11-04 定稿，之前两种做法都不对）：

1. 文本按句拆组（每 2 句一组）；
2. **只等第一组合成完就返回** → 播放立刻开始，不用等整篇；
3. 其余组在**播放期间**后台合成（单卡串行、双卡两路并行）；
4. 播放器播完一组 → `GET /voice-player/next-group` 取下一组；已合成好就无缝接播，没合成完返回 `pending`（400ms 重试）；
5. 某组合成失败就跳过（不会卡住整条）。

| 做法 | 结果 |
| --- | --- |
| 整篇合成完再拼成一个文件（v0.5.12~0.5.15） | 长文要干等几十秒才出声 |
| 播完一组才去合成下一组 | 两句之间空等，像卡带 |
| **边播边合成（现在）** | 第一句秒出，后面的在播报期间备好 |

- **单次 ≤120 字（约 30 秒）**：播报期间麦克风是关的，超过这个长度的内容会把用户的话吞掉或挤到队尾（2026-11-04 实测：整篇《岳阳楼记》107 秒，用户同一句说了两遍，agent 只看到一条）；
- 更长的内容拆成 2–3 次 `voice_say`，**连着发完、中间不夹 `voice_wait`**（2026-11-05 用户定）：第一组立刻出声、其余组在后台合成、客户端按顺序连播；夹一次 `voice_wait` 反而把播报切成一段一段。全部发完再 `voice_wait` 等回声；
- 连发期间麦克风整段是关的：用户要插话，靠悬浮条上的「打断」（打断会连队列一起停，且不会再把被打断的片段自动捡回来重播）；
- `voice_say` 的返回里带 `warn` 字段提醒超长，`groups` 字段告诉你拆了几组；
- 需要整段拼成一个文件时仍可用 ffmpeg **重新编码**（`-c:a libmp3lame -b:a 96k`），`-c copy` 会把第二段拼成噪声。

### 2.6.5 音频播放为什么走代理

气泡里的 `<audio>` 必须指向**页面同源**的 `/voice-player/audio?file=xxx`（host 转发到 18082 的 `/say-file/`）。
直接指向 `127.0.0.1:18082` 会被页面 CSP 拦截——表现是“点了播放没反应、随后变灰”。

### 2.7 半双工与播放队列

页面上任何 `<audio>` 在播放时，录音自动暂停（每 250ms 轮询所有 audio 的 paused/ended 状态），播完自动恢复。
所以**我说话时你插话会被丢掉**——这是已知代价。

**播放队列（2026-11-04 修正）**：

- agent 连发多条语音（长文拆 2–3 次时很常见）→ 客户端**按顺序排队**，前一条没播完（包括它渐进的各组）绝不插新的；
- `/voice-player/last-voice` 会带回 `history`（最近 12 条，正序），客户端轮询间隔 1.2 秒也漏不掉挨得近的两条；
- 每条语音有自己的 `voice id`，取后续分组时带上（`/voice-player/next-group?voice=…`）；agent 中途又发一条时，老的那条只会拿到 `done`，不会串到新消息的组上；
- 点悬浮条下方的黄「打断」= 停当前播放 **+ 清空整个队列**（用户要它闭嘴，不是排着队继续念）。

### 2.8 文件通道（**每个会话独立一套**）

| 项 | 值 |
| --- | --- |
| 写入端点 | `POST /voice-call/inbox`（voice-player host 提供，body 里带 `sessionId`） |
| 目录 | `D:\Harness工作区\会话\流式语音输入可行性\输出\calls\<sessionId>\` |
| 文件 | 该目录下 `voice-inbox.jsonl`、`voice-inbox.read`、`voice-heartbeat.txt` |
| 每行 | `{"t":<毫秒时间戳>,"type":"start"|"speech"|"end","text":"...","callId":"c…"}` |
| 已读标记 | 同目录 `voice-inbox.read`（一个行号，由 `voice_call_status` / `voice_wait` 自动写） |

- **为什么按会话分文件**：以前所有会话共用一个 `voice-inbox.jsonl`，上一通电话的 `end` 会串进下一次通话，agent 一读就误判「已挂断」（2026-11-04 连踩两次）。现在每个会话一个目录，历史互不干扰；
- `sessionId` 由客户端在接通时取当前会话 id 一并 POST；取不到就落到 `calls\default\`；
- 目录名做过净化（非 `[A-Za-z0-9_.-]` 一律换成 `_`），不会因为 id 里带路径分隔符写飞；
- 宿主返回 `inbox` 字段给出真实路径，agent 不需要自己拼——`voice_call_status` / `voice_wait` 都会回；
- 旧版本写在 `输出\voice-inbox.jsonl`（全局那份）的历史数据不再参与判定，可以留着备查。

## 二点九、播放器渲染：规则与坑（2026-11-03 实测定稿）

### 结论

| 发送方式 | 结果 | 原因 |
| --- | --- | --- |
| `voice_say` 工具输出 | ❌ 不出卡片 | 输出落在**工具卡片**里：卡片带折叠按钮 → `guardsOk()` 拒绝；文本还会被截断 → 解析也失败 |
| 正文消息里的**纯标记** | ✅ 出卡片 | 整条消息就是一个标记，解析与 guard 都能过 |
| 用户录的语音（带「转写：」） | ✅ 出卡片 | 2026-11-03 修了正则：`转写` 前允许换行，且宽松匹配把转写整段认作标记的一部分 |

### 正确做法

1. **先用 `voice_say` 合成**（它只保证音频文件生成成功，**不保证出卡片**）；
2. 再用脚本生成标记，**单独发一条正文消息**：

```powershell
py.cmd dsh-tools\voice-mark.py --file <文件名>.mp3 --secs <时长>
```

3. 把输出那一行**原样**作为一条消息发出：前后不加任何字、不用代码块、不写 Markdown 链接。

### 曾经的坑（别再踩）

- **工具卡片里永远渲染不出**——别再指望 `voice_say` 直接出播放器；
- **标记前后加文字**（残留 >24 字）→ 解析器放弃；
- **一条消息里两个「【」** → 拒绝；
- **URL 与「转写」之间夹换行**（老正则要求紧邻）→ 曾导致用户语音全部不渲染，已修；
- **音频必须走同源代理**（`/voice-player/audio?file=`），直接指向 18082 会被页面 CSP 拦（表现为点了没反应、随后变灰）。

### 自查

```powershell
curl.exe -s "<GUI 地址>/voice-player/bubble-report?all=1"
```

看 `count`：0 = 一条都没渲染。页面 Console 里跑 `window.__voiceDebug()` 还能看每个标记元素的 `parsed/loose/guard`。

## 三、语音消息（录音）

1. 点输入框左侧声波按钮（服务没起会先拉起 TTS）；
2. 录音中显示秒数，超过 30 秒自动结束；
3. 录完上传到 host 端点 `POST /voice-player/upload`：存文件到 `D:\py-tts\out\`、调 18080 转写；
4. 结果进**待发托盘**（「录好了 · 待发 N 条」），按发送才发出去；
5. 发送后气泡渲染成原生 `<audio>` 播放器。

> 上传走插件自己的 host 端点，**与 TTS 后端解耦**——GPU 档（Qwen3-TTS）和 CPU 档（CosyVoice2）都能录。
> 旧版直连 TTS 服务的 `/upload`，CPU 档没有该端点，就会「录不进去」。

## 四、服务与档位

### 4.1 两个服务

| 端口 | 服务 | 模型 | 说明 |
| --- | --- | --- | --- |
| 18080 | Qwen3-ASR | **0.6B** | 转写；GPU |
| 18082 | TTS | 见下方双后端 | 合成 |

### 4.2 TTS 双后端（按设置里的「运行位置」切换）

| 档位 | 起的进程 | 特点 |
| --- | --- | --- |
| **GPU** | `qwen_tts_server.py`（`.venv-qwen`） | Qwen3-TTS 0.6B，热态约 1.2s/句，占约 2.3G 显存；**该库只能 GPU**（CUDA graph 写死） |
| **CPU** | `tts_server.py`（普通 `.venv`，`CUDA_VISIBLE_DEVICES=""`） | CosyVoice2 0.5B，克隆参考音色 `voice-me.wav`，0 显存、热态约 3.3s/句 |

两者都用 **18082** 端口输出/播放，`voice_say` 无需关心后端是谁。

### 4.3 驻留方式

- **常驻**：模型加载后一直留着（推荐：避免「停一会儿再说」时那 15 秒冷加载）；
- **空闲卸载**：空闲 N 秒后卸掉模型（省显存/内存，代价是下一次请求要重新加载）。

### 4.4 显存预期

| 场景 | 大约 |
| --- | --- |
| 各模型都卸载 | ~4G（基础占用） |
| TTS 常驻 | +2.3G |
| 通话中（TTS + ASR 同时加载） | 7–8G |
| 再叠加 27B 之类的大模型 | 会顶到 20G+（那时语音会变卡） |

## 四点二、CPU 档的速度（2026-11-03 实测）

| 场景 | 耗时 |
| --- | --- |
| 首次请求（加载模型） | ~20 秒 |
| 热态每句（20 字左右） | 5–6 秒 |
| 极短句（10 字内） | 3–4 秒 |

速度由模型本身决定（0.5B 在 CPU 上自回归逐字生成，随句长线性增长）。要快就用 GPU 档或 GPU×2。

**启动服务时会自动预热**（合成一句 + 转写一段静音），所以点完启动、等它就绪后，第一句交流就是热态，不用再等冷加载。

### 改过服务端代码要重启

改过 `tts_server.py` / `qwen_tts_server.py` 之后**必须重启对应服务**——模型是进程内加载的，旧进程会一直跑旧代码。排查看 `D:\py-tts\logs\tts-stderr.log`。

## 四点五、混合加速（**当前暂停**，面板灰掉）

CPU+GPU 混合档暂时不可用：实测里它会放大故障（CPU 侧一慢，整条合成跟着失败），已从面板禁用（按钮灰、点不了）。

- 默认档位：**GPU（Qwen3-TTS）**；
- 要更多吞吐：**GPU×2**；
- CPU 档保留，面板已标注「速度可能较慢：约 5–6 秒/句」。

## 四点五、混合加速与音色（重要）## 四点五、混合加速与音色（重要）

混合加速（CPU+GPU）会**同时用两个不同的模型**合成同一段话：

| 档位 | 谁在合成 | 音色来源 |
| --- | --- | --- |
| GPU / GPU×2 | Qwen3-TTS（faster 库） | 参考音频 `voice-me.wav` |
| CPU | CosyVoice2 | 参考音频 `voice-me.wav` |
| **混合** | 前者 + 后者各合成一部分再拼接 | **两个模型各自的音色** |

**两个模型对同一段参考音频的还原程度不同，所以混合档的接缝处音色可能有可感知的差异**（面板里也有加粗提示）。

### 准备音色时的正确做法

**GPU 和 CPU 两边的音色要一起训练/一起配参考**，不要只配一边：

1. **同一段参考音频喂给两边**：`voice-me.wav`（16k 单声道）同时作为 Qwen3-TTS（GPU）与 CosyVoice2（CPU）的参考；
2. **参考文本要和音频逐字一致**（`--prompt-text`），错一个字音色就会跑偏；
3. **两边都试听一遍**再定稿：同一段参考，Qwen3 和 CosyVoice2 的输出会有差别，挑两边都还能接受的那版参考；
4. 想进一步对齐，可以用 **GPU 合成一段参考、喂给 CPU 侧克隆**——实测可能让 CosyVoice2 长句出现含糊/胡言乱语，需先用短句验证；
5. 混合档只适合“能接受一点音色差异”的场景；要求完全一致就用 **GPU×2**（同模型，代价 +2.3G 显存）。

## 五点五、客户端版本升级的影响与修复

插件本身在磁盘上（`dsh-plugins\voice-player`），**升级客户端不会删它**；风险全在**客户端内部接口**是否仍兼容。

### 依赖的客户端接口

| 接口 | 用在哪 | 升级风险 |
| --- | --- | --- |
| `sessions.retain(id)` → `binding.session.prompt/cancel` | 通话开始注入消息、挂断强制中止回合 | **中高**：`cancel()` 是内部方法，可能改名/改签名 |
| `shell.overlay` 槽位 | 通话悬浮条 | 中：槽位名或 props 变化会不渲染 |
| `conversation.input.left` 槽位 | 输入框左侧录音按钮 | 中：同上 |
| `ctx.tools.register` / `ctx.webServer.register` | `voice_say` 工具、`/voice-player/*` 端点 | 低：宿主 API 较稳 |
| `config.json` 里的 device / mode | 服务档位 | 无：纯本地文件 |

### 升级前（十分钟）

1. 备份插件目录：`voice-player` → `voice-player.bak-升级前`；
2. 备份 profile 的 `cordis.patch.yml`（照例带 `.bak-日期`）；
3. 记下当前 `config.json`（哪个档位、常驻/空闲）。

### 升级后按顺序验（断哪步修哪步）

| 步 | 验证 | 断了怎么修 |
| --- | --- | --- |
| 1 | 点「语音服务」→ 灯绿 | 查 `/voice-player/status` 是否 200；灰了看 host 是否加载（profile 里 `voice-player` 行） |
| 2 | 录一条语音 → 能转写进托盘 | 录音走 `/voice-player/upload`（host 端点），坏了看 18080 是否活着 |
| 3 | 通话能开麦、句子能进 `voice-inbox.jsonl` | 写入端 `/voice-call/inbox`；检查 host 端点注册日志 |
| 4 | agent 能读文件并回语音 | `voice_say` 工具是否注册；`/say` 能否 200 |
| 5 | **挂断是否瞬停** | 若又变成「靠 agent 读到 end」→ `session.cancel()` 失效：把 `client.js` 挂断段的 cancel 调用降级成只写 `end`，等确认新 API 名再补 |
| 6 | 悬浮条可拖动、齿轮可开面板 | 拖拽是纯前端，不受升级影响；不渲染先怀疑槽位 |

### 修复原则

- **优先降级，不硬刚**：内部 API 失效时先退回「不依赖它」的路径（例如挂断退回写 `end`、由 agent 读到收尾），保证功能可用；
- **再找新接口**：在 `node_modules/@deepseek-ai/dsh-api-session-controller` 之类的包里搜 `cancel` / `interrupt`，确认新方法名后替换；
- **改动都留备份**：`client.js.bak-*` / `services.js.bak-*`，出问题可逐文件回退。

## 五点八、其他坑

- **CPU 合成慢**：先确认 INT8 量化生效（见「CPU 档必须开 INT8 量化」），否则 20 字要 20 秒以上。

- **CosyVoice2 长文本会截断**：一次给很长的一段，它合成到中途就收尾（实测 200 字只出了 17 秒）。CPU 档调用时要**按段落拆开**逐段合成再拼接（插件内的分组就是干这个的）。
- **混合档音色差异**：见「混合加速与音色」一节。

## 五点九、TTS 输入限制（会崩的写法）

**TTS 不是"喂多少都行"**：一次塞超长文本、或者同时投入很多短句，服务会被打崩（合成失败 / 进程卡死）。

### 正确写法

1. **单条 ≤ 600 字**，超了就分条；
2. **按句拆开，一段一段喂**——插件内部已经按「每 2 句一组」拆分，并且**并发上限为 2**（一次最多两路同时合成）；
3. 长文朗读（几百字以上）宁可**分多次发**，每段之间留出合成时间；
4. 合成失败时先看 `voice_say` 的报错摘要（现在会带 error 前 80 字）和 `D:\py-tts\logs\tts_service.log`。

## 六、已知限制与坑

- **TTS 拼接**：必须重新编码，`-c copy` 会让第二段变噪声（已改用 libmp3lame）。
- **两个 TTS 服务的输出目录**：本机都是 `D:\py-tts\out`，但若换机器部署需确认一致，否则 `/say-file/` 播不到。
- **半双工**：我说话时你插话会被丢（采集暂停），要「打断」需另做回声消除双工。
- **断句**：静音 **2 秒**（`config.json` 的 `call.silenceMs`，范围 600–3500）。太短会抢话（曾用 500ms，用户没说完就回；也试过 900ms，用户觉得"话还没落就被截"）。
- **`faster_qwen3_tts` 不支持 CPU**：它抛 `CUDA graphs require CUDA device`；CPU 档一律走 CosyVoice2。
- **挂断后偶尔多一句**：点击挂断与最后一帧采集可能撞车（毫秒级），一般不影响。
